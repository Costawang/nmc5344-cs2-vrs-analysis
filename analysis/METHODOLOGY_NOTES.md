# Methodology notes

## Observation and publication

The project studies official published standings, not latent team ability. Snapshot date, commit/publication timestamp and collection timestamp are separate concepts. A later revision to an old date is preserved; the final version available at the pinned repository commit is used for canonical analysis. The original revision remains in the raw archive and versioned standings table.

The monthly invitation series is the primary sampling frame. Live entries that duplicate it are not additional observations. Extra live dates and early Git-history snapshots support supplementary trajectories. The irregular 2024 publication schedule is not treated as a regular weekly time series. No daily interpolation is performed.

The canonical global dataset prefers invitation over live on an overlapping date, then uses live or legacy where no invitation list exists. March 2024 regional lists remain in the long source table because no official global list was published. They are not merged into an invented official global ranking using rounded points.

## Identity

The source team name is retained verbatim after display-markup cleanup. Nicknames are Unicode NFC normalised, lowercased and trimmed for comparison; punctuation remains significant. The sorted unique nickname set is hashed into an analytical roster signature. No permanent player identifier is claimed.

A core lineage connects consecutive sampled snapshots only when both displayed rosters have five distinct players, at least three are shared, and the pair is each other's unique highest-overlap match. This deterministic convention is inspired by the model's overlap logic, but is not an exact reconstruction of Valve's internal roster construction. Lineages are built separately for all snapshots and for the monthly series; identifiers from those sequences are not interchangeable.

An unchanged set shares five players; one- and two-player changes share four and three. A same-name pair sharing at most two players is a major-replacement candidate and starts a new lineage. A core continuing under a different team label may remain one analytical lineage without declaring the two organisations identical. Ambiguous matches and incomplete rosters remain unresolved. An unlinked complete roster starts a new lineage; after a gap it is not silently joined back to an earlier lineage.

Manual decisions, if needed, must be recorded in `config/identity_overrides.csv` with entry IDs, `link`/`break`, a public evidence URL and a note. Overrides never edit raw files. No unsupported external transfer-history enrichment is used. Exact-roster Top 10 retention is reported alongside core retention as an identity sensitivity check.

## Missingness and arithmetic

Blank CSV cells represent missing/not-applicable values as described by each column. The original `-` in contribution tables means the report did not present that selected contribution; it is not automatically numeric zero, and it does not prove the match was online. Separate `*_reported` flags preserve this distinction.

Published integer points and one-decimal final rank values are separate observed fields. Formula reconciliation allows 0.16 points for the sum of printed components. Integer points are checked within 0.56 points of the printed detail value. Raw component values and parenthesised adjusted values are stored separately.

The winnings table lists selected ranking contributions, not necessarily all a team's actual earnings. It lacks permanent event IDs and event names. Its rows are not joined across snapshots using dates alone. Early snapshots can include matches or prize events before 2024 because the ranking window looks backwards; these inputs are preserved as context, even though the ranking observations start in 2024.

## Match contributions

`match_id_local` is generated by the upstream loader for each calculation. The project key is an entry plus a contribution-row ordinal, retaining the displayed local ID as a value. Both sides of a match and repeated appearances in later snapshots are retained as different ranking contributions. Summing these rows across snapshots would double count matches and mix different age weights.

A match-level deduplicated population, causal transfer study or independent VRS recomputation is outside this release. Valve's public detail reports and sample JSONs do not provide all the stable identifiers and complete input history needed for those claims.

## Measures

- Top 10 retention = shared core-lineage members between adjacent monthly Top 10 sets / 10. Entrants = 10 minus retained members. Transitions involving unresolved relevant identity are unavailable rather than assigned a reassuring zero.
- Exact-roster retention uses the displayed normalised five-player set, making it intentionally more sensitive to lineup changes. The headline sensitivity comparison uses the same evaluable transitions as core retention; the all-complete-roster estimate is reported separately.
- Rank improvement = previous rank minus current rank, so positive means improvement. Changes require consecutive calendar months in the same lineage.
- Point change = current points minus previous points, only in consecutive months within the same broad model period. Raw-point SD is likewise period-specific and requires at least three observations.
- Rank percentile = 1 - (rank - 1)/(number ranked - 1). It is a relative within-list measure; changing eligibility and denominator still affect interpretation.
- Volatility summaries require at least six ranked months and three consecutive-month comparisons. Rank SD uses all observed full ranks; mean absolute change uses only adjacent-month pairs. Observation counts and coverage accompany the summaries.
- Consecutive Top 10 runs count observed monthly snapshots, not daily occupancy. A missing/non-Top-10 month breaks a run.
- Top 10 entry/exit counts use presence in each monthly Top 10 list. An absent lineage is outside that observed Top 10 set, without imputing its rank. The first month is left-censored; no entry is counted before it. Counts remain dependent on lineage segmentation and identity uncertainty.
- Three-month cases use exact calendar-month separation. Largest rise/decline are selected among volatility-eligible lineages; the stable example must have reached Top 10. Ties use coverage, mean rank and displayed name.

Sampling only today's top teams would induce survivor bias. This project defines elite coverage from all observed months and reports roster/lineage observation coverage. Monthly lineage IDs can end when continuity cannot be established; results are therefore sensitive to both sampling frequency and the continuity convention.

## Method periods

Broad boundaries are 2024-04-22, 2024-07-11, 2025-01-01, 2025-02-24, the first July 2025 snapshot after regional changes, and the first September 2025 snapshot after the August change. These are analytical segmentation choices, not an assertion that the displayed snapshot was generated with a provably exact code version. The January filtering commit was published later than its match-date threshold. Changes to invitation regulations are tracked separately from scoring-code changes.

Even within a code period, points depend on relative component normalisation, eligible teams and the moving match window. Period segmentation reduces obvious inconsistencies but does not create a universal skill scale. Rank and Top-N comparisons can also respond to rule changes. The report therefore provides a comparison excluding transitions across these broad periods.

Regional composition begins in July 2025 after the single-region change. Earlier assignments are retained as a separate one-to-many table. Match dates are used as printed; the model formats some dates in America/Los_Angeles. They are not reinterpreted as exact local timestamps.

## Integrity and reproducibility

Git archives are exported with `core.autocrlf=false` and `core.eol=lf`. Raw files are copied without text conversion and checked against Git blob sizes, SHA-256 manifests and source Git object hashes. The first/last seen timestamps describe the inspected mainline history and its pre-period baseline, not necessarily the original creation date of a pre-period sample. Unknown schemas stop parsing and appear in an error table.

Data validation includes uniqueness, link coverage, official rank agreement, roster agreement, printed-score reconciliation, weights, date order and raw checksums. A fresh R session reproduces processed tables from locked source versions. The archived JS model is inspected as source evidence but is not executed as a replacement ranking model.
